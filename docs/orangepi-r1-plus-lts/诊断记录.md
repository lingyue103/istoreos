# WAN 口无法上网 —— 诊断记录（已解决）

**结论：根因是设备树（DTS）用了错误的 RGMII 延迟配置，已定位并修复。**

---

## 1. 现象

前两版自编译镜像（iStoreOS 24.10 内核 6.6）：

- 系统能正常启动，LuCI 能进
- WAN 口（`eth0`，原生 GMAC）**链路能协商成功**：`Link is Up - 1Gbps/Full`
- `rx_errors=0` `rx_crc_errors=0`
- 但 **只能发不能收**：
  - DHCP discover 发出去，**收不到任何 OFFER**
  - 配静态 IP 后 `arping` 网关：`probes 6 FAILED`
- 同一根网线、同一个上游路由器，刷**官方 OpenWrt 21.02 / snapshot v1.6** 固件
  则一切正常（`eth0` 拿到 `192.168.8.154`，ping 网关 0% 丢包）

→ **硬件、网线、上游都没问题，故障在我们的构建里。**

## 3. 关键突破：对比能上网的官方固件

从能正常联网的官方 `OpenWrt21.02-release_OrangePi_R1_Plus_LTS_v2.0.0` 镜像里，
把 boot 分区的 `rockchip.dtb` 解出来对比：

**官方可用固件（内核 5.4 BSP）：**
```
ethernet@ff540000 {
    phy-mode = "rgmii";
    tx_delay = <0x19>;
    rx_delay = <0x05>;
    snps,reset-delays-us = <0x00 0x3a98 0xc350>;
    mdio {
        ethernet-phy@0 {          <-- PHY 地址 = 0
            reg = <0x00>;
            keep-clkout-on;
            reset-gpios = <0x24 0x12 0x01>;
        };
    };
};
```

**我们第一版 24.10 构建的 DTB（推断 + dmesg 佐证）：**
- dmesg 打印 `init for RGMII`、`TX delay(0x19)`、`RX delay(0x5)`
  → 说明用的是 **MAC 端延迟**写法，且 PHY 按非 LTS 版处理

这就是问题所在：**延迟加错位置了。**

## 4. 根因（上游已有明确修复补丁）

Orange Pi R1 Plus **LTS** 的 WAN PHY 是 **YT8531C**，MDIO 地址 **0**；
而普通版 R1 Plus 用的是 RTL8211E，地址 **1**。

LTS 版必须由 **PHY 内部**添加 RGMII 延迟（`phy-mode = "rgmii-id"`），
把延迟加在 MAC 端（`rgmii` + `tx_delay`/`rx_delay`）会导致
**链路 Up 但收不到包**。

上游 Linux 内核 2025 年 1 月专门为此提交了补丁：

> *"In general the delay should be added by the PHY instead of the MAC, and this
> improves network stability on some boards which seem to need different delay."*
>
> ```
> Fixes: 387b3bbac5ea ("arm64: dts: rockchip: Add Xunlong OrangePi R1 Plus LTS")
> Cc: stable # 6.6+
> ```
> 已在 3 块板子上测试通过
>
> — [PATCH] arm64: dts: rockchip: change eth phy mode to rgmii-id for orangepi r1 plus lts
> https://lists.openwrt.org/pipermail/linux-rockchip/2025-January/055025.html

补丁内容正是：
```diff
 &gmac2io {
      phy-handle = <&yt8531c>;
-     tx_delay = <0x19>;
-     rx_delay = <0x05>;
+     phy-mode = "rgmii-id";
```

社区也有同样症状的 issue：
[OrangePi R1 Plus LTS无法使用WAN口 · coolsnowwolf/lede#10980](https://github.com/coolsnowwolf/lede/issues/10980)

## 7. 第二个问题：登录后 502（同一版已修复）

### 现象
刷入 v4 后，后台登录页**能正常显示**，输入账号密码点击登录 → **502 Bad Gateway**，
之后打不开。重启、换浏览器都无效。

### 根因
v4 误带了 iStoreOS 新的 `istorenext` 前端（nginx + uwsgi）。引入链条是：

```
luci-app-istorex  →  luci-mod-istorenext  →  luci-nginxer  →  luci-nginx  →  nginx
```

而 `luci-mod-istorenext` 的 nginx 规则 `root/etc/nginx/conf.d/istorenext.locations`：

```nginx
location ~ ^/cgi-bin/luci/istorenext(/|$) {
    if ($login_request = 0) {
        proxy_pass http://127.0.0.1:8080;      # ← 死路
    }
}
```

全树搜索 `8080` 只有一处会提供监听，而且位于 **`root-demo/`**（演示用，生产不安装）：

```
luci-mod-istorenext/root-demo/etc/init.d/istorenext-demo:
  procd_set_param command /usr/sbin/uhttpd ... -p 0.0.0.0:8080
```

所以：
- **登录页能显示** → 它由 uwsgi 动态渲染，说明 uwsgi 是活的（这条也证明你的 root 密码
  大概率已经写进去了，因为 argon 主题的登录表单 `action="<%=REQUEST_URI%>"`，
  POST 走的是同一条 uwsgi 链路）
- **点登录即 502** → 登录成功后跳转到 `luci-mod-istorenext` 的首页
  `/cgi-bin/luci/istorenext`（它的菜单 `order` 是 0），正好命中上面那条
  `proxy_pass http://127.0.0.1:8080` → 没有进程监听 → 502

### 对照官方 R2S 固件（关键证据）
把用户手上的官方 `istoreos-25.12.5-...-r2s-squashfs.img.gz` 挂载后逐包比对：

| | 官方 R2S | v4（502） |
|---|---|---|
| Web 服务器 | `uhttpd` + `uhttpd-mod-ubus` | `nginx-ssl` + `uwsgi` |
| nginx 包数量 | **0** | 6+ |
| `/etc/nginx` | 不存在 | 存在（含 istorenext 规则） |
| LuCI 入口 | `/www/cgi-bin/luci`（ucode CGI） | nginx `uwsgi_pass /var/run/luci-webui.socket` |
| `luci-mod-istorenext` / `luci-app-istorex` / `luci-nginxer` | **均无** | 均有 |
| 主题 | `luci-theme-argon` / `luci-theme-bootstrap` | 多一个 `luci-theme-istorenas` |

结论：**`istorenext`/`istorex` 那套不是官方 R2S 的形态**，而且它依赖的 8080 后端
根本不在我们的软件源里。

### 修复
Web 栈整体换成官方同款：

- 启用：`uhttpd`、`uhttpd-mod-ubus`、`px5g-mbedtls`、`luci-ssl`、`luci-light`

## 9. 关于 balenaEtcher 的报错（不影响写入）

现象：
```
出现了点问题。如果源镜像曾被压缩过，请检查它是否已损坏
the writer progress ended unexpectedly
```

原因：OpenWrt 会在 `.img.gz` 的 gzip 流**之后**追加 288 字节 sysupgrade 元数据
（JSON + 签名）。balenaEtcher 底层用 Go 的 `gzip.Reader`，它读完一个成员后会尝试
读"下一个 gzip 成员"，碰到这段数据（头两字节是 `0000`，不是 gzip 魔数 `1f8b`）就抛
`gzip: invalid header`。

用 Go 实测确认（构建机上编译了一个和 Etcher 同款的小程序）：

```
原始镜像:  解压字节数 941621760 → 报错 gzip: invalid header
去掉尾巴:  解压字节数 941621760 → 正常结束
```

**关键结论：解压字节数分毫不差，写入是完整的。** 最有力的证据是 —— Etcher 报错之后
设备照样开机、照样出登录页。所以这个报错是 Etcher 校验步骤自身的问题，与镜像内容无关。

处理：本版交付的镜像已去掉那 288 字节尾部元数据，Etcher 不会再报错；
解压后与标准版**逐字节相同**（已用 sha256 比对确认）。

## 10. 【最终结论】WAN 口的真正根因：PHY 参考时钟被配成 25 MHz

前面第 8、9 节里"把 `phy-mode` 改成 `rgmii-id` 就修好了"的结论**是错的**，
这里更正。真正的根因是**时钟**，而且是**在真机上读寄存器一步一步实测出来的**，
不是推断。

### 10.1 机理

* R1 Plus LTS 的 DTS 里 `clock_in_out = "input"`，意思是
  **RK3328 GMAC 的参考时钟不来自 SoC，而来自 YT8531C PHY 的 CLKOUT 引脚**，
  必须是 **125 MHz**。
* PHY 扩展寄存器 `0xa012` 控制这个时钟输出。实测值 **`0x00c8`** = 选了
  **25 MHz 参考源**（`CLK_SRC_REF_25M`）；正确值应为 **`0x00d0`**
  （`SYNCE_ENABLE` + `CLK_FRE_SEL_125M` + `CLK_SRC_PLL_125M`）。
* 25 MHz 的后果非常典型：**接收正常、发送是死的**。
  链路能协商到 1 Gbps、PHY 能看到对端、内核能收到包，但本机发出的帧对端收不到。
  表现出来就是 **DHCP 拿不到 OFFER、ARP 无应答、ping 100% 丢包**。

### 10.2 为什么内核"看起来设对了"却还是错

* DTS 里明明写着 `motorcomm,clk-out-frequency-hz = <125000000>`（已从 FIT 里的 DTB 核对）；
* 上游 `motorcomm.c` 的 `yt8531_probe()` 也确实会把它写成 125 MHz；
* **但 `yt8531_probe()` 只在 probe 那一次执行**，而 `phy_init_hw()` 每次都做
  **「软复位 → config_init」**，软复位会把 `0xa012` 打回硬件默认的 `0x00c8`，
  而上游的 `yt8531_config_init()` **从来不重新写这个寄存器** → 于是复位后永远是 25 MHz。
* 香橙派厂商版驱动是在每次 reset 之后重新应用的，所以厂商固件正常、主线内核不正常。

### 10.3 实测证据（对照组）

用自写的一个 aarch64 静态 MDIO 工具（`mdio`，见 `diag.sh` 同类工具）在设备上直接读写寄存器：

复位前（已手工修好）／复位后（`ip link set eth0 down; up`）：

| 寄存器 | 复位前 | 复位后 |
|---|---|---|
| `0xa012` | `0x00d0` ✅ | `0x00c8` ❌ |
| `0x000c` | `0x8006` | `0x8000` |

**只写 `0xa012 = 0xd0`（完全不碰 `0x0c`）**，然后立刻跑 DHCP：

```
udhcpc: broadcasting select for 192.168.8.63, server 192.168.8.1
udhcpc: lease of 192.168.8.63 obtained from 192.168.8.1, lease time 43200
2 packets transmitted, 2 packets received, 0% packet loss   # ping 192.168.8.1
```

→ **单写这一个寄存器就完全恢复联网**，`0x0c`（时钟门控寄存器）那笔是多余的，
所以最终补丁里没有它。

反面验证：写完 `0xd0` 之后如果再做一次 `ip link set eth0 down/up`，
联网立刻又坏 —— 这恰恰从反面证明了"复位会抹掉配置"这个机理。

### 10.4 最终修复：内核补丁（已固化进镜像）

新增补丁（**仅 1 个 hunk，630 字节，最小改动**）：

```
target/linux/rockchip/patches-6.12/990-net-phy-motorcomm-reapply-clk-out-config.patch
```

内容就是在 `yt8531_config_init()` 的末尾（`yt8531_set_ds()` 之后、`return 0` 之前）
重新调用一次 `yt8531_probe(phydev)`：

```c
	ret = yt8531_probe(phydev);
	if (ret < 0)
		return ret;
```

`config_init` 在**每次 PHY 复位之后都会由 `phy_init_hw()` 调用**，
所以复位再也抹不掉 125 MHz 的配置了。

补丁的正确性做了交叉验证：用**未经修改的原始 `motorcomm.c`** 应用该补丁，
结果与构建树里的源码**逐字节一致**。

> 中途踩过的坑：第一版补丁在 `yt8531_probe()` 里引入了 `ret = ...`，
> 但该函数**没有声明 `ret`**（只有 `node` / `mask,val` / `freq`），
> 会直接编译失败。已修正为不改 `yt8531_probe()` 的方案。

### 10.5 被排除的可能性（都有硬证据）

RGMII 延迟（`rgmii` / `rgmii-id` 两种都试过，MAC 侧 `0x19`/`0x05` + 使能位也试过）、
强制 100 Mbps、SoC pad 驱动能力（与厂商 DTB 完全一致 8ma/4ma）、PHY pad 驱动、

## 11. IPv6（默认开启）实测记录

用户要求：**固件默认打开 WAN 和 LAN 的 IPv6**。

### 11.1 原厂状态就是开着的，但有一处"隐形关掉"

实测设备（本固件）状态：

```
network.wan6      = interface, device=eth0, proto=dhcpv6     ← WAN 有 DHCPv6 客户端
network.lan.ip6assign = 60                                   ← LAN 下发 /60 前缀
dhcp.lan.ra       = server        dhcp.lan.dhcpv6 = server   ← LAN 有 RA + DHCPv6 服务端
dhcp.lan.ra_slaac = 1             ra_flags = managed-config other-config
/etc/rc.d/S35odhcpd 存在（开机自启）
/proc/sys/net/ipv6/conf/{all,eth0,br-lan}/disable_ipv6 = 0   ← 内核三个接口全开
odhcpd 监听 [::]:547,  odhcp6c 监听 [::]:546
```

**但发现一处真正会"关掉 IPv6"的默认值**：dnsmasq 的

```
option filter_aaaa 1        # 过滤掉 DNS 里的 AAAA 记录
```

这等于对外默默关掉了 IPv6 解析（iStoreOS 为"提速"而设）。**已改为 `0`**。

### 11.2 LAN 侧 IPv6 端到端实测（通过 ✅）

接在 LAN 口的下游 Windows 主机自动获得：

```
fd7e:2a7:27ea:0:a8b5:645:1de5:8bdc   RouterAdvertisement（SLAAC）
fd7e:2a7:27ea:0:1633:e9e1:6c60:cc24  RouterAdvertisement（SLAAC）
fd7e:2a7:27ea::e00                   Dhcp（DHCPv6）
```

→ **RA + SLAAC + DHCPv6 三条路全部工作**，下游设备无需任何配置即可获得 IPv6 地址。

### 11.3 WAN 侧拿不到公网 IPv6 —— 原因在上游，不在固件

在 eth0 上抓上游 RA，内容是：

```
ICMP6, router advertisement, length 56
    hop limit 64, Flags [none], pref high, router lifetime 0s
    source link-address option: 44:df:65:5f:4e:a1
    mtu option: 1500
    rdnss option: fd... fe80::46df:65ff:fe5f:4ea1
```

即上游 `fe80::46df:65ff:fe5f:4ea1`（MAC `44:df:65:5f:4e:a1`）：

* **`router lifetime = 0s`** → 明确声明"我不是默认网关"；
* **完全没有 Prefix Information Option** → 不发布任何前缀；
* 也不回应 DHCPv6（`udhcpc`/`odhcp6c` 拿不到 ADVERTISE）。

这是"上游根本没开 IPv6"的典型特征。所以 R1 的 `eth0` 只有 `fe80::` 链路本地地址，
换任何固件、任何路由器都是这个结果。**根因是上游（光猫/上级路由/运营商）没下发 IPv6 前缀。**

本固件的默认配置对"上游给前缀"的情况**可以自动适配**：只要上游下发前缀
（RA 带 PIO 或 DHCPv6-PD），`wan6` 会自动拿到地址，LAN 会自动把前缀通过 RA/DHCPv6
分给下游设备，**不需要改任何设置**。

### 11.4 为此固化进固件的改动

1. `package/network/services/dnsmasq/files/dhcp.conf`：`filter_aaaa` 默认 **1 → 0**；
2. 新增 `package/base-files/files/etc/uci-defaults/95-ipv6-defaults`（幂等）：
   确保 `wan6`（dhcpv6，device eth0，`reqaddress=try`、`reqprefix=auto`）、
   `lan.ip6assign=60`、`dhcp.lan.ra/dhcpv6=server`、`ra_slaac=1`、
   `ra_flags=managed-config other-config`、`dhcp.wan.ignore=1`、
   `odhcpd` 各项、`dnsmasq.filter_aaaa=0`，并启用 `odhcpd`/`odhcpd-state` 开机自启。
   只在缺项或被改成 `disabled` 时才修正，不覆盖用户自己的调整。

> 这样即使以后 board.d / uci-defaults 的行为变化，固件的 IPv6 默认开启也有保障。

### 11.5 为什么 `CONFIG_PACKAGE_dnsmasq-dhcpv6` 没选是正确的

IPv6 的 RA/DHCPv6 服务端由 **odhcpd**（`odhcpd-ipv6only`）提供，dnsmasq 只做
DHCPv4 + DNS，所以不需要 dnsmasq 的 DHCPv6 变体。这与官方 R2S 固件的做法一致。
