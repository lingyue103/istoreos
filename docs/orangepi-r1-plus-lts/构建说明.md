本文档记录**本项目固件的完整可复现构建流程**，包含环境、命令、坑位和我实际用到的
排查/验证方法。所有内容都是在这台机器上真实跑通并逐条记录下来的，不是照抄官方文档。

## 1. 构建环境

* **系统**：Ubuntu 22.04 / 24.04（本项目在 **WSL2 + Ubuntu 24.04** 下完成）
* **磁盘**：源码树 ~350 MB，但完整编译后 `build_dir + staging_dir + bin` 约 **25~35 GB**
  —— 请预留 **≥ 40 GB** 可用空间
* **内存**：8 GB 以上（本项目 10 GB，串行编译通过；内存不足会在链接阶段被 OOM Kill）
* **CPU**：核数越多越好，但**不要用 `-jN`（N>1）**，原因见第 5 节

安装依赖：

```sh
sudo apt update
sudo apt install -y build-essential ccache ecj fastjar file g++ gawk gettext git \
  java-propose-classpath libelf-dev libncurses5-dev libncursesw5-dev libssl-dev \
  python3 python3-distutils python3-setuptools python3-dev rsync subversion \
  swig time xsltproc zlib1g-dev unzip
```

> WSL 用户注意：请把 Windows 路径从 `PATH` 里去掉，否则交叉编译会误用 Windows 工具链：
> ```sh
> export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
> ```
> （`.wslconfig` 里的 `appendWindowsPath=false` 在本机没生效，所以每次构建都显式设一遍最稳。）

`feeds.conf.default` 的内容（分支必须对得上 25.12）：

```
src-git packages https://github.com/jjm2473/packages.git;istoreos-25.12
```

> **如果 GitHub 连不上**（国内很常见）：本项目当时的做法是手动把各 feed 的 zip 解压到
> `feeds/<名字>/`，然后**绝对不要再跑 `scripts/feeds update`**（会覆盖掉手工放置的内容）。
> 记得 `feeds/luci/luci.mk` 必须存在，否则 LuCI 相关包全部编译不出来。

## 4. 配置

```sh
# 直接用本项目导出的最小配置：
cp docs/orangepi-r1-plus-lts/config.diff .config
make defconfig
```

或者自己 `make menuconfig` 选：

```
Target System   -> Rockchip
Subtarget       -> armv8
Target Profile  -> Xunlong Orange Pi R1 Plus LTS
Target Images   -> Kernel partition size (MiB) = 16
                   Root filesystem partition size (MiB) = 864
```

⚠️ **rootfs 必须放大到 864 MiB**：内置 Docker 之后原默认分区装不下，
否则打包阶段会报：

```
ext4_allocate_best_fit_partial: failed to allocate 1521 blocks
```

（`CONFIG_TARGET_KERNEL_PARTSIZE=16` / `CONFIG_TARGET_ROOTFS_PARTSIZE=864`）

## 5. 编译

```sh
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
export FORCE_UNSAFE_CONFIGURE=1
export GOPROXY=https://goproxy.cn,direct
export GOSUMDB=off

# 关键：串行编译
make -j1 V=s 2>&1 | tee build.log
```

### 为什么必须 `-j1`

这个树**并行编译（`-j8` 之类）会出现连锁失败**：某个包偶发失败后，
后续包会因为依赖状态被污染而接连报错，最后的错误信息还指向别的地方，极难定位。
`-j1` 慢但稳，本项目全程串行，一次通过。

### 为什么要在后台跑

如果挂在交互终端里，终端一断线（SSH 超时、窗口关闭）会发 SIGHUP 把 make 杀掉，
日志里表现为莫名其妙的 `target/linux failed to build`。正确姿势：

```sh
setsid nohup env PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin \
  FORCE_UNSAFE_CONFIGURE=1 GOPROXY=https://goproxy.cn,direct GOSUMDB=off \
  make -j1 > build.log 2>&1 < /dev/null &
```

然后 `tail -f build.log` 看进度。

### 耗时参考（本机实测）

| 阶段 | 耗时 |
|---|---|
| 内核全量重编（`make target/linux/clean` 之后） | 约 34 分钟 |
| 软件包编译 + 打包 | 约 25 分钟 |
| 首次完整编译（含交叉工具链、全部依赖） | 明显更长，建议留出几小时 |

> 另外提醒：`target/install` 阶段 kmod 包会调用内核的 `make modules`，
> 有时会触发**整树内核重编**（日志上看像是"又编了一遍"）。这是正常现象，等它跑完即可。

## 6. 产物与校验

```sh
ls -l bin/targets/rockchip/armv8/
# istoreos-rockchip-armv8-xunlong_orangepi-r1-plus-lts-squashfs-sysupgrade.img.gz   ← 要刷的
# istoreos-rockchip-armv8-xunlong_orangepi-r1-plus-lts-ext4-sysupgrade.img.gz       ← ext4 变体
# ...manifest / sha256sums / profiles.json
```

### 关于 balenaEtcher 报错（重要）

OpenWrt 会在 `.img.gz` **末尾追加 288 字节的 sysupgrade 元数据**。
Go 写的解压器（Etcher 用的）遇到这段尾巴会报：

```
the writer progress ended unexpectedly
```

**写入本身是完全成功的**（解压后字节数分毫不差，设备照样能开机）。

解决办法是去掉这 288 字节：

```sh
SZ=$(stat -c %s image.img.gz)
head -c $((SZ - 288)) image.img.gz > image-cleaned.img.gz
```

去掉之后 Etcher 不再报错，且解压结果与标准版**逐字节相同**（务必自己校验一遍）：

```sh
gzip -dc 标准版.img.gz | wc -c
gzip -dc 清理版.img.gz | wc -c     # 两个数字必须一样
```

代价：没有元数据就不能用 LuCI 的「刷写固件」再刷它（全新刷机不受影响）。

## 7. 把这套修复用到别的板子 / 平台

核心补丁是**通用**的，不只是 R1 Plus LTS：

1. 把 `990-net-phy-motorcomm-reapply-clk-out-config.patch` 复制到你源码树的
   `target/linux/<你的平台>/patches-<内核大版本>/` 下；
2. 确认目标板的 DTS 里 PHY 节点同时满足：
   * `clock_in_out = "input"`（GMAC 参考时钟来自 PHY）
   * `motorcomm,clk-out-frequency-hz = <125000000>`
   * PHY 是 YT8531 / YT8521 系列

   可以这样检查：

   ```sh
   grep -rn "clk-out-frequency-hz" target/linux/*/files*/arch/*/boot/dts/
   grep -rn "clock_in_out" target/linux/*/files*/arch/*/boot/dts/
   ```

3. 重新编译内核即可。

## 8. 常见错误速查（本项目全部踩过）

| 报错 / 现象 | 原因 | 处理 |
|---|---|---|
| `docker` 编译报 `error: remote origin already exists` | `feeds/packages/utils/{docker,dockerd}` 的 `Build/Prepare` 会 `git fetch` github.com 校验 commit | 打 `docs/orangepi-r1-plus-lts/feeds-docker-offline-all.patch`（仅去掉联网校验，Commit 字符串改用 Makefile 里硬编码的，与上游一致） |
| `docker-compose` 卡在 `go list`，`ss -tnp` 看到 SYN-SENT 到 `proxy.golang.org` | Go 模块代理不通 | `export GOPROXY=https://goproxy.cn,direct GOSUMDB=off`（`golang-values.mk` 会自动继承） |
| `ppp` 报 `error: 'VERSION' undeclared` | 残留的 `config.h` | `make package/network/services/ppp/clean` 后重编 |
| 中途 `make: *** Hangup` / 莫名 `target/linux failed to build` | 终端掉线 SIGHUP | 用 `setsid nohup ... &` 跑（见第 5 节） |
| `ext4_allocate_best_fit_partial: failed to allocate ... blocks` | rootfs 分区太小 | `CONFIG_TARGET_ROOTFS_PARTSIZE=864` |
| `luci-app-store` 编译失败 | 需要预编译的 UI 包 | 把 `istore-ui-v0.2.0-2.tar.gz` 放进 `dl/` |
| 某个包失败后一堆包接连失败 | 并行编译污染依赖 | 改 `-j1` 重来 |
| APK 源 404 / `apk update` 报 kmods 行失败 | 自编译内核模块哈希与官方仓库不一致 | **正常现象**，所有自编译 OpenWrt 都这样，不影响使用 |

## 9. 怎么验证固件真的修好了

刷完后 SSH 进设备，**不要做任何手工修复**，检查这几项：

```sh
# 1) PHY 驱动绑定是否正常
dmesg | grep -iE 'YT8531|motorcomm|stmmac'
#   期望：eth0: PHY [stmmac-0:00] driver [YT8531 Gigabit Ethernet]

# 2) WAN 是否自动拿到 IP（这是关键）
ubus call network.interface.wan status | grep -E '"up"|address'
ip -4 -br addr show eth0
ping -c3 223.5.5.5

# 3) IPv6 是否默认开启
uci show network | grep -E 'wan6|ip6assign'
uci show dhcp    | grep -E 'ra|dhcpv6'
uci -q get dhcp.@dnsmasq[0].filter_aaaa      # 应为 0
ip -6 addr show br-lan
```

### 进阶：直接读 PHY 寄存器确认（最有说服力）

如果手边有 MDIO 工具（`phytool` / 自己写的小工具），读扩展寄存器 `0xa012`：

```
0x00d0  → 125 MHz，正确 ✅
0x00c8  → 25 MHz，坏的 ❌
```

⚠️ 注意：**不要**在修复生效后再做 `ip link set eth0 down/up`。
那会触发 PHY 软复位 —— 在**没有本补丁**的固件上会把配置打回 25 MHz；
在**有本补丁**的固件上则会在复位后自动重新写回 125 MHz（这正是补丁的意义）。
