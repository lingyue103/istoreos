## 二、这一版真正修好了什么

### 问题 1（核心）：WAN 口拿不到 IP —— PHY 参考时钟被配成了 25 MHz

**根因不是 RGMII 延迟，是时钟。** 这一条是**在真机上读寄存器实测确认**的，
不是靠推测：

* 板子 WAN 口是 **YT8531C** PHY（MDIO 地址 0），DTS 里是 `clock_in_out = "input"`，
  意思是 **RK3328 GMAC 的参考时钟由 PHY 的 CLKOUT 引脚提供**，必须 125 MHz。
* 实测 PHY 扩展寄存器 `0xa012` = **`0x00c8`** → bit4=0 → **CLKOUT 输出 25 MHz**（错的）。
  需要的是 **`0xd0`**（bit7 `SYNCE_ENABLE`、bit4 `CLK_FRE_SEL_125M`、bit3:1 `CLK_SRC_PLL_125M`）。
* 25 MHz 的后果：**发送时钟是死的、接收完全正常** —— 链路能协商到 1Gbps、能收到包，
  但本机发出去的帧发不出去。表现就是 DHCP 拿不到 OFFER、ARP 无应答。
* 为什么内核里明明有 `clk-out-frequency-hz = <125000000>`（125 MHz）却还是错的：
  `yt8531_probe()` **只在 probe 那一次**把 CLKOUT 设成 125 MHz，而 **PHY 每次软复位
  （`phy_init_hw()` / `phy_start()`）都会把 `0xa012` 复位回默认的 `0xc8`**，
  上游驱动的 `yt8531_config_init()` 从来不重新写一遍。树莓派/香橙派厂商版驱动是在
  重置之后重新应用的，所以厂商固件正常、主线内核不正常。

**决定性验证**：用自写的一个小 MDIO 工具在设备上运行

```sh
mdio eth0 0 w 0xa012 0x00d0     # CLKOUT 改 125MHz
mdio eth0 0 m 0x000c 0x0006 0x0006
udhcpc -i eth0 -f -n -t 5 -T 3 -A 2 -q -v
```
→ **立刻拿到 IP（192.168.8.63），`ping 192.168.8.1` 0% 丢包**。
（注意：之后**不能**再 `ip link set eth0 down/up`，那会触发软复位把改动抹掉 ——
这恰好反过来证明了上面的机理。）

**固件的修复方式**（已打进内核，永久生效）：
新增内核补丁
`target/linux/rockchip/patches-6.12/990-net-phy-motorcomm-reapply-clk-out-config.patch`

内容只有一处（**最小改动**）：在 **`yt8531_config_init()`** 的末尾重新调用一次
`yt8531_probe(phydev)` —— 而这个函数在**每次 PHY 复位之后都会被 `phy_init_hw()`
调用**，所以复位再也抹不掉 125 MHz 的配置了。

**已在本机真机上端到端验证通过**：把新内核换到板子上重启，**不做任何手工修复**：

```
PHY 扩展寄存器 0xa012  = 0x00d0          ← 125 MHz，重启+复位后依然正确
wan 接口               = "up": true, proto dhcp
eth0 地址              = 192.168.8.66/24
默认路由               = default via 192.168.8.1
ping 223.5.5.5         = 0% packet loss
DNS 解析 baidu.com     = 正常
```
（`dmesg` 里 PHY 被重新配置了两次、含一次 Link Down/Up，寄存器仍为 `0xd0` ——
恰好覆盖了以前会失效的那个场景。）

> 早先版本按上游 2025-01 的 DTS 补丁把 `phy-mode` 改成 `rgmii-id`，
> **那并不是本板不联网的根因**，本版仍保留该正确写法，但真正解决问题的是上面这个 PHY 时钟补丁。

### 问题 2：登录后 502

原因：早先的版本误带了 iStoreOS 的 `istorenext`（nginx+uwsgi）前端。
它的 nginx 规则把 `/cgi-bin/luci/istorenext*` 反代到 `127.0.0.1:8080`，
而那个端口在这个镜像里**没有任何服务** → 登录后跳转即 502。

本版把 Web 栈换成**官方 R2S 同款**：

| | 官方 R2S | 本版（已对齐） |
|---|---|---|
| Web 服务器 | uhttpd | **uhttpd** ✅ |
| LuCI 入口 | `/www/cgi-bin/luci`（ucode CGI） | 同 ✅ |
| nginx / uwsgi | 无 | **无** ✅ |
| 主题 | argon / bootstrap | argon / bootstrap ✅ |

nginx / uwsgi / `/etc/nginx` / `/etc/uwsgi` 已全部移除，开机只有 `S50uhttpd`。

### 问题 3：IPv6 默认开启（按你的新要求）

**本版固件默认就是开 IPv6 的，WAN 和 LAN 都是**，并且已经用**实测**验证过（见第七节）：

| 位置 | 默认配置 |
|---|---|
| **WAN**（eth0） | `network.wan6`：`proto=dhcpv6`、`reqaddress=try`、`reqprefix=auto`（DHCPv6 + 接受上游 RA/SLAAC） |
| **LAN**（br-lan） | `network.lan.ip6assign=60`，odhcpd 提供 **RA + DHCPv6 服务器**，`ra_slaac=1`，RA 标志 `managed-config` + `other-config` |
| **DNS** | dnsmasq `filter_aaaa=0`（**不过滤 AAAA 记录**，否则等于对外关掉了 IPv6 解析） |
| 内核 | `disable_ipv6=0`（三个接口全是 0） |

为了不依赖隐式行为、避免以后被改掉，这些设置被**固化进固件**：
新增 `/etc/uci-defaults/95-ipv6-defaults`（幂等，只在缺项或被人为关掉时才修正），
同时 dnsmasq 的出厂 `dhcp.conf` 里 `filter_aaaa` 默认值已改为 `0`。

## 三、刷机

### 准备
- ≥ 2 GB 的 TF 卡（或通过 USB 读卡器写板载 eMMC）
- 工具：**balenaEtcher** 或 **Rufus**（Rufus 请选「DD 镜像模式」）

### 写入
1. 选择设备 → 选择镜像 → 开始
2. 若提示「trailing garbage / 尾部数据」之类，**忽略即可**，不要中断写入
   （本版镜像已去掉尾部元数据，正常应该不会有任何警告）
3. 写完安全弹出

> **关于 Etcher 的校验报错**：如果你用旧镜像时见过
> "the writer progress ended unexpectedly"，那只是 Etcher 校验步骤的问题 ——
> 证据是报错之后设备照样能开机、能出登录页，说明写入是成功的。本版镜像已消除该报错。

### 开机
1. TF 卡插进板子，接网线，上电
2. **首次启动需要 1~2 分钟**（生成配置、初始化 overlay），耐心等

### 网口对应关系（很关键）
| 口 | 设备名 | 位置 |
|---|---|---|
| **WAN** | `eth0` | 原生 GMAC + YT8531C，**远离 USB 接口的那个网口** |
| **LAN** | `eth1` | USB 网卡 RTL8153，**与 USB 接口同侧的那个网口** |

> 电脑要接在 **LAN 口**才能访问后台。拿不准就两个口都插，看哪个先通。

## 五、WAN 口怎么确认真的通了

登录后 SSH 执行：

```sh
ubus call network.interface.wan status | grep -E 'up|address'   # 应能看到 IPv4 地址
ping -c3 223.5.5.5
```

如果 WAN 拿不到地址，先看这行（**这是本板的命门**）：

```sh
dmesg | grep -iE 'YT8531|motorcomm'
ip -br addr show eth0
```

## 六、IPv6 怎么用 / 怎么查

### 6.1 你自己怎么验证

在**接在 LAN 口**的电脑上看：

* **Windows**：`ipconfig` 里应该出现一个 `fdxx:...` 或运营商前缀的 IPv6 地址
* **Linux/macOS**：`ip -6 addr` / `ifconfig` 看 `inet6`
* LuCI 里「网络 → 接口」应该能看到 `WAN6` 和 `LAN` 都有 IPv6 地址

在路由器上：

```sh
uci show network | grep -E 'wan6|ip6assign'
uci show dhcp    | grep -E 'ra|dhcpv6'
ip -6 addr show br-lan
logread | grep odhcpd
```

### 6.2 WAN 侧能不能拿到公网 IPv6，取决于你的上游

**这一点必须说清楚**：固件这边已经全开了，但**能不能拿到公网 IPv6 地址，
取决于上级设备/运营商给不给**。

实测本机的上游（192.168.8.1 那台）是这样：

```
ICMP6, router advertisement: hop limit 64, Flags [none], pref high,
                             router lifetime 0s
   source link-address option: 44:df:65:5f:4e:a1
   mtu option: 1500
   rdnss option: fe80::46df:65ff:fe5f:4ea1
```

即：**它只发 RA，而且 `router lifetime = 0s`、完全没有 Prefix Information Option
（不发布任何前缀），也不回应 DHCPv6。** 这是"上游根本没开 IPv6"的典型特征，
所以 R1 的 WAN 口只有链路本地地址 `fe80::...` —— **换任何固件、任何路由器都是这个结果**。

想让 WAN 拿到公网 IPv6，需要：
1. 运营商那条线本身支持 IPv6（很多家庭宽带默认给了，但光猫/上级路由没开）；
2. 上级设备开启 IPv6，并**下放前缀**（RA 带 PIO，或做 DHCPv6-PD 前缀委派）。

本固件的默认配置对这两种情况**都能自动适配**：上游只要下放前缀，
`wan6` 会自动拿到地址，LAN 会自动通过 RA/DHCPv6 把前缀分给下游设备，不用你改任何设置。

### 6.3 实测结果（本机环境）

| 项目 | 结果 |
|---|---|
| WAN（eth0）IPv6 | 只有 `fe80::` 链路本地地址（**上游不发前缀**，见 6.2） |
| LAN（br-lan）IPv6 | `fd7e:2a7:27ea::1/60`（ULA）✅ |
| odhcpd | 运行中，监听 `[::]:547` ✅ |
| odhcp6c | 运行中，监听 `[::]:546` ✅ |
| **下游 Windows 主机** | 拿到 `fd7e:2a7:27ea:0:...`（**RA/SLAAC**）和 `fd7e:2a7:27ea::e00`（**DHCPv6**）✅ |

最后一行是关键：**LAN 的 IPv6 是真正在工作的**，RA + SLAAC + DHCPv6 三条路都通，
下游设备自动就能拿到 IPv6 地址。

## 九、已知事项

- 自定义编译的内核模块哈希与官方仓库不一致，所以 `apk update` 时
  **kmods 那一行会 404**，这是所有自编译 OpenWrt 的共有现象，不影响使用。
  官方源里的用户态软件包（luci-app-diskman 等）不受影响。
  脚本 `istore-install` 已能容忍这一项失败。
- 本镜像去掉了尾部 sysupgrade 元数据，因此**不适合**用 LuCI 的「刷写固件」功能
  再刷它（那需要元数据）。做全新刷机完全没影响。若要恢复元数据版，
  在 `归档_旧镜像\` 里有标准版可参考。
- 镜像体积比常规 OpenWrt 大，是内置 Docker 所致。
- 本固件带了自制内核补丁（PHY CLKOUT 125 MHz 重应用）。**升级到官方 iStoreOS
  同版本镜像后 WAN 会再次失效**，因为那里面没有这个补丁。要升级请用本项目重新编译。
